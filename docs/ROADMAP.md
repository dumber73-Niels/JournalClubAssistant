## 1. 요구사항별 비판적 검토

### 1.1 논문 유형별 처리

**동의하는 점**: 유형마다 구성과 읽는 법이 다르다. 같은 3단계를 모든 논문에 적용하면 체계적 문헌고찰에서는 "선행연구 흐름 정리"가 논문 본문과 겹치고, 종설(narrative review)에서는 "방법 보강"할 대상이 거의 없다.

**보완할 점**

1. **유형을 더 나눠야 한다.** "Original article" 안에서도 설계마다 확인할 내용이 다르다.

   | 유형 | 보고 지침 (구성 확인용) | 비뚤림·질 평가 도구 |
   |---|---|---|
   | 무작위 임상시험(RCT) | CONSORT | RoB 2 |
   | 관찰연구 (코호트, 환자-대조군, 단면) | STROBE | ROBINS-I / ROBINS-E, NOS |
   | 진단 정확도 연구 | STARD | QUADAS-2 |
   | 동물실험 (첫 사례) | ARRIVE 2.0 | SYRCLE RoB |
   | 체계적 문헌고찰 / 메타분석 | PRISMA 2020 | AMSTAR 2, ROBIS |
   | 종설 (narrative review) | SANRA | SANRA |
   | 증례보고 / 증례군 | CARE | JBI 체크리스트 |
   | 진료지침 / 합의문 | RIGHT | AGREE II |
   | 시험관 연구 (in vitro) | (표준 지침 약함) | 자체 체크리스트 |

2. **3단계를 유형별로 다시 정의한다.**

   | 단계 | Original article | SR / MA | Narrative review |
   |---|---|---|---|
   | ① 맥락 | 선행연구 흐름, 연구팀 계보 | 이 리뷰 이전의 리뷰들과의 관계, 이 리뷰가 메우는 공백 | 리뷰가 다루는 분야의 지도, 저자의 관점과 이해상충 |
   | ② 보강·검증 | 생략된 방법을 인용 문헌에서 보강, 인용 정확성 점검 | 프로토콜(PROSPERO), 검색식, 포함·제외 연구 목록, 보충자료에서 빠진 내용 보강, 포함 연구 몇 편의 원문 대조 | 핵심 주장마다 인용한 1차 연구가 실제로 그 주장을 지지하는지 점검, 빠진 주요 연구 탐색 |
   | ③ 결과 해석 | 효과 크기, 통계, 한계 | 숲 그림(forest plot) 다시 읽기, 이질성, 출판 비뚤림, GRADE 근거 수준 | 주장-근거 대응표, 근거 수준별 정리 |
   | 산출물 | 학습 PDF + 발표 슬라이드 | 같음 + 포함 연구 요약표 | 같음 + 주장-근거 지도 |

3. **유형 판별은 자동 + 사용자 확인으로 한다.** PubMed의 출판 유형(Publication Type) 정보를 먼저 쓰고, 없으면 LLM이 판별한 뒤 사용자가 확인한다. 잘못 판별하면 이후 전 과정이 틀어지므로 확인 단계를 생략하지 않는다.

4. **보충자료(supplementary material)를 입력으로 받아야 한다.** 특히 SR/MA는 검색식과 포함 연구 표가 보충자료에 있는 경우가 많다. 본문 PDF만으로는 2단계가 부실해진다.

### 1.2 Windows / Mac 프로그램

**동의하는 점**: 대상 사용자(교수, 레지던트)는 명령줄보다 설치형 프로그램이 익숙하다.

**문제점과 수정**

1. **엔진 먼저, 앱은 나중에.** PDF 해석, 문헌 조회, LLM 호출, 산출물 생성은 화면과 무관한 부분이고 가장 어렵다. 이것을 Python 라이브러리 + CLI로 먼저 완성하고 평가한 뒤 앱을 씌운다. 그래야 화면을 고치느라 핵심 품질 개선이 밀리지 않는다.

2. **기술 선택 (권장안)**

   | 부분 | 권장 | 이유 |
   |---|---|---|
   | 엔진 | Python | PDF·과학 문헌 처리 도구(PyMuPDF, GROBID 연동), 문서 생성(python-pptx, 보고서 PDF)이 가장 풍부 |
   | 데스크톱 셸 | Tauri 2 (+ Python 엔진을 함께 묶어 실행) | Electron보다 설치 파일이 작고 메모리를 적게 씀. 대안: Electron(자료가 더 많음), PySide6(Python만으로 가능하나 화면 품질이 떨어짐) |
   | 화면 | 웹 기술 (React 등) | 중간 결과(마크다운)를 보고 고치는 편집 화면이 필요 |
   | 로컬 저장 | 파일 폴더 (문헌당 기록 파일) | 개인 문헌 보관함, 메타데이터, 작업 이력 |

3. **배포에 드는 비용과 절차를 미리 계획한다.**
   - **macOS**: Apple Developer 계정(연 99달러)으로 서명과 공증(notarization)을 하지 않으면 "확인되지 않은 개발자" 경고로 실행이 막힌다.
   - **Windows**: 코드 서명 인증서가 없으면 SmartScreen 경고가 뜬다. 병원 PC는 서명 없는 프로그램 설치를 막는 경우가 많다.
   - **자동 업데이트**: 처음부터 넣어야 나중에 배포가 편하다.

4. **병원 PC 환경을 고려한다.**
   - **사용 환경 (확인됨)**: 업무용 PC는 EMR/OCS/PACS 망으로 분리되어 있고, 개인 PC·노트북은 인터넷이 되는 별도 와이파이를 쓴다. 따라서 **대상은 레지던트의 개인 노트북(Windows/Mac)**이며 업무용 PC 설치와 완전 오프라인 모드는 고려하지 않는다.
   - **관리자 권한**: 개인 노트북이므로 큰 제약은 아니지만, 사용자 폴더 설치를 기본으로 한다.

### 1.3 LLM 연결 방식

**동의하는 점**: 사용자마다 쓸 수 있는 LLM이 다르므로 여러 방식을 지원해야 한다.

**문제점과 수정**

1. **구독 계정(ChatGPT Plus, Claude Pro 등) 직접 연결은 빼는 것을 권장한다.**
   - 소비자용 구독은 원칙적으로 해당 회사의 앱 안에서 쓰도록 되어 있고, API 사용권을 포함하지 않는다.
   - 제3자 프로그램이 구독 계정으로 로그인해 모델을 호출하는 것은 대부분 약관상 허용되지 않거나 별도 승인이 필요하다. 비공식 방법으로 구현하면 계정 정지 위험이 있고, 언제든 막힐 수 있다.
   - 정책은 자주 바뀌므로, 구현 시점에 각 회사의 최신 약관을 다시 확인한다.

2. **기본 경로: MCP 서버로 구독 사용자를 지원한다.**
   - 이 프로그램의 기능(PDF 해석, PubMed 조회, 인용 대조, 슬라이드 생성)을 MCP(Model Context Protocol) 서버로 제공한다.
   - 사용자는 Claude Desktop 같은 공식 앱에 이 서버를 연결하고, 자기 구독으로 대화하듯 작업한다. 약관 문제 없이 구독을 활용하는 정식 경로다.
   - 이번 첫 사례도 사실상 이 방식(구독 기반 에이전트 + 도구)으로 만들어졌다.
   - 설계 원칙은 1.6절.

3. **API 키 연결 (보조, CLI와 조건부 데스크톱 앱용)**: Anthropic, OpenAI, Google을 우선 지원한다.
   - 키는 OS 보안 저장소(Windows 자격 증명 관리자, macOS 키체인)에 저장하고 파일에 평문으로 두지 않는다.
   - 작업 전에 예상 비용을 보여 준다(논문 1편 처리에 수십만 토큰이 들 수 있음).
   - 반복되는 긴 입력(논문 본문)에는 프롬프트 캐싱을 써서 비용을 줄인다.

4. **로컬 모델**: llama.cpp, Ollama, LM Studio 같은 OpenAI 호환 서버로 연결한다.
   - 한계를 정직하게 안내한다. 일반 노트북의 로컬 모델은 긴 논문(수만 토큰)을 다루기 어렵고, 의학 추론이 클라우드 모델보다 약할 수 있다.
   - **원문 처리 위치 분리**: 구독 원문(1.8절의 L 등급)은 노트북 밖으로 보내지 않는다. 추출 코드와 로컬 모델이 노트북 안에서 처리하고, 클라우드 모델에는 사용자가 확인한 사실·메모와 서지 정보만 넘긴다. CC 라이선스 원문(F 등급)은 클라우드로 전문을 처리한다.
   - **로컬 모델은 선택 사항이다.** 없어도 추출 코드와 읽기 양식으로 동작하고, 있으면 사용자가 직접 써야 할 문항이 줄어든다. 공개 사용자에게 고가 하드웨어를 요구하지 않는다.
   - 권장 구성: 로컬 모델은 원문 대조와 추출에, 클라우드 모델은 종합과 비판적 평가에 쓰는 **작업별 모델 배정**을 지원한다.

   **첫 시험 결과 (2026-10-27, jpis-56-189 한 편)**: qwen3.8-flash-next(4비트급 압축 IQ4_XS, llama.cpp, 컨텍스트 262,144, 사용자 PC "edgexpert")로 1·2단계를 수행해 Claude 기준 결과와 비교했다.

   | 항목 | 한국어 출력 | 영어 출력 |
   |---|---|---|
   | 지어낸 참고문헌 | 0건 | 0건 (PMID 44개 실재 확인) |
   | ref 30의 JEL·BCL 정의 누락 발견 | 발견 | 발견 |
   | ref 29(임플란트주위염 리뷰) 인용 문제 | "배경 인용으로 적절"로 누그러뜨림 | 원문을 열어 가장 분명한 인용 문제로 판정 |
   | 1·2단계 사이 모순 | 1건 ("저자가 한계로 인정"이라고 잘못 씀) | 없음 |
   | 언어 품질 | 중국어 한자 혼입, 어색한 단어 | 문제없음 |
   | 처리 시간 (도구 사용 에이전트) | 20분 33초 | 17분 48초 |

   - 도구 없이 전문만 넣은 1회 호출은 비판적 평가(대조군 사료, SRP 비교, ARRIVE 누락)에 강했고, 도구를 쓰는 에이전트는 원문 대조에 강했다. → 처리 흐름에서 **원문 대조 단계와 비판적 평가 단계를 따로 둔다.**
   - 생각(추론) 토큰을 많이 쓴다. 출력 한도 16,000토큰에서는 답이 비었고 40,000토큰에서 정상 종료했다. → 출력 한도를 충분히 주고, 빈 답을 오류로 처리한다.
   - 남은 오류: 다른 문헌의 PMC 번호를 잘못 붙임(1건), 받아 둔 초록을 "서지 확인"으로 낮게 표시, 같은 사실을 두 파일에서 다르게 씀. → 서지 ID 자동 대조와 단계 간 일관성 검사로 잡는다.
   - 시험 중 Claude 기준 결과의 오류 1건도 찾았다(전작이 Ireson 2004를 인용하지 않았다고 잘못 씀). 기준 결과도 검증 대상이다.
   - 논문 한 편의 결과이므로, 평가 세트로 다시 확인한 뒤 하드웨어와 모델 배정을 정한다.

5. **모델 종류와 무관하게 지킬 원칙**
   - **LLM은 참고문헌을 만들어 내지 않는다.** 모든 인용은 PubMed, Crossref, OpenAlex에서 조회한 실제 문헌 ID(PMID, DOI)에 연결된 것만 쓴다.
   - **모든 주장에 출처 문장과 확인 수준을 붙인다**: 전문 확인 / 초록 확인 / 2차 자료 / 확인 못 함 (첫 사례의 표기 방식).
   - 출력은 정해진 구조(JSON 스키마)로 받아 검증한다.

### 1.4 원문 접근

**동의하는 점**: 기관 구독으로 최근 논문 원문을 볼 수 있고, 원문이 있어야 2단계(방법 보강)가 제대로 된다.

**문제점과 수정**

1. **프로그램이 자동으로 원문을 대량 다운로드하는 기능은 넣지 않는다.**
   - 출판사와 기관의 계약은 대부분 자동·대량 다운로드를 금지한다. 이를 어기면 **기관 전체의 접근이 차단**될 수 있다.
   - 텍스트·데이터 마이닝(TDM)은 출판사가 제공하는 별도 API와 등록 절차로만 허용되는 경우가 많다.

2. **대신 "사용자가 직접 받도록 돕는" 흐름을 만든다.**
   - **기관 인증 방식 (확인됨)**: 출판사 구독은 병원 인터넷 와이파이의 **IP 기반 인증**이다. 병원 와이파이에 연결된 노트북에서는 DOI 링크만으로 원문이 열린다. 병원 밖(집 등)에서는 도서관 프록시나 VPN이 필요하므로, 링크 화면에 "병원 와이파이에서 열기" 안내를 함께 표시한다.
   - MCP 서버는 사용자 노트북에서 실행되므로 요청은 그 노트북의 IP에서 나간다. 그러나 **프로그램이 출판사 사이트에서 직접 PDF를 받는 기능은 여전히 넣지 않는다.** 병원 IP 전체가 출판사에서 차단되면 모든 구성원이 피해를 입는다.

   1. PDF의 참고문헌을 구조화하고 DOI, PMID를 찾는다.
   2. 각 문헌에 대해 링크를 만든다: DOI 링크(병원 와이파이에서는 이것으로 충분), **기관 프록시 링크**(병원 밖 사용 시, 기관별로 한 번 설정), PubMed 링크.
   3. 사용자가 클릭하면 **평소 쓰는 브라우저**에서 열리고, 기관 인증도 브라우저가 처리한다.
   4. 사용자가 PDF를 내려받으면, 프로그램이 다운로드 폴더를 감시하다가 DOI로 해당 문헌과 짝지어 개인 문헌 보관함에 넣는다.
   5. 아직 원문이 없는 문헌은 "초록 기준"으로 표시하고, 필요한 문헌 목록을 보여 준다.

3. **오픈 액세스 원문은 공식 API로 직접 가져온다.**
   - Unpaywall: DOI로 합법적인 무료 원문 위치와 라이선스·판본 조회. 구독 논문이라도 CC 라이선스가 붙은 저자 원고나 프리프린트가 있으면 그 판본을 가져온다 (1.8절)
   - Europe PMC / PubMed Central OA: 구조화된 전문(XML). 첫 사례에서도 이 경로로 전작의 측정 방법을 확인했다
   - OpenAlex, Crossref, Semantic Scholar: 메타데이터, 인용 관계

4. **10년이 넘은 문헌을 고려한다.** 연구 흐름의 뿌리는 오래된 논문인 경우가 많다(첫 사례: 1981, 1983, 1991년 문헌). 도서관에서 스캔본 PDF로 받을 수 있으므로 스캔본 처리를 지원한다(1.5절). 구할 수 없으면 초록으로 처리하고 그렇게 표시한다.

### 1.5 스캔본 PDF (클래식 논문)

도서관이 보내 주는 스캔본으로 시험했다 (Löe, Theilade, Jensen. Experimental Gingivitis in Man. J Periodontol 1965, 11쪽, 600 dpi 흑백).

**시험 결과**

| 항목 | 결과 |
|---|---|
| 텍스트 층 | 출판사가 디지털화하며 넣은 OCR 텍스트 층이 이미 있었음. 오래된 논문도 출판사 사이트에서 받은 PDF는 이런 경우가 많다 |
| 본문 단어 | 기존 텍스트 층과 Tesseract 5 결과를 비교하면 약 4,900단어 중 2.9%가 다름. 대부분 줄 끝 하이픈과 대소문자 차이로 의미 없는 차이 |
| 의미 있는 오류 | 움라우트가 있는 이름 깨짐(Löe → "L e", Mühlemann → "M hlemann"), 숫자 분리("1950" → "19 50"), 'the' → 'trie', 'GI' → 'Gl', 범위 표기 하이픈 누락("0.1 - 1.0" → "0.1 1.0"), 두 단 편집에서 일부 읽는 순서 섞임 |
| 표 숫자 | 표 1, 4의 숫자 78개는 두 방식 모두 정확 |
| 그래프 (그림 2-4) | 막대·영역 모양이라 OCR로는 값을 얻을 수 없음 → 이미지 LLM으로 설명하고 "그림에서 읽은 근사값"으로 표시 |
| 표 자동 검증 | 각 행의 평균을 다시 계산해 표기값과 비교. 6행 중 1행 불일치(표 1, 계산 1.679 vs 표기 1.67) → 이미지 확인 결과 **OCR이 아니라 원문 자체의 값**. 자동 검증은 "다시 볼 곳"을 찾아 주고, 원인 판정은 사람이 한다 |

**Docling 비교 시험 (CPU 4코어, 11쪽)**

텍스트 층을 지운 "이미지만 있는 PDF"를 만들어 도서관 스캔본과 같은 조건에서 비교했다. 기준값은 고해상도 이미지로 확인한 표 숫자 165개.

| 방식 | 시간 | 표 숫자 165개 중 오류 | 본문 점검 10항목 | 비고 |
|---|---|---|---|---|
| 출판사 텍스트 층 + Docling | 58초 | 1 ("1.19" → "1-19") | 9 | 출판사 텍스트 층도 틀릴 수 있음. 그림 1 캡션 없음 |
| 이미지만 + Docling 내장 Tesseract | 87초 | 115 | 6 | 표를 칸 단위로 잘라 읽어 숫자 대부분 손상 ("0.54" → "OM") |
| 이미지만 + Docling 내장 RapidOCR | 98초 | 4 | 8 | 칸 병합 오류, 0.53 → "03", 단어 사이 공백 누락 |
| **이미지만 → OCRmyPDF → Docling** | **13초 + 41초** | **1** ("0.15" → "06.15", 평균 검사로 검출) | **8** | **가장 좋음**. 첫 글자 장식(drop cap) 누락, 움라우트 일부 누락 |

- Docling은 텍스트 층이 있을 때 두 단 편집의 읽는 순서와 범위 하이픈("0.1 - 1.0")을 단순 텍스트 추출보다 잘 복원했다.
- Docling 안에서 OCR을 돌리는 것보다, **OCRmyPDF로 페이지 전체 텍스트 층을 먼저 만들고 Docling은 구조 정리만 맡기는 것**이 빠르고 정확했다.
- 어떤 방식도 숫자 오류가 0은 아니었다. 표 일관성 검사와 두 번째 판독이 반드시 필요하다.

**설계 반영**

1. 텍스트 층 유무를 먼저 확인한다. 없으면 OCRmyPDF(Tesseract 기반)로 텍스트 층을 만든다. 있어도 품질 점수가 낮으면 다시 OCR한다.
2. **숫자·단위·표·그래프는 두 경로로 읽는다**: OCR 텍스트와 이미지 LLM. 결과가 다르면 원본 이미지 조각과 나란히 보여 주고 사용자가 확정한다.
3. **표 내부 일관성 검사**를 자동으로 한다: 평균·합계·백분율 재계산, n 합계, 범위 확인. 불일치는 "OCR 오류 의심"과 "원문 자체 불일치"를 구분해 기록한다.
4. 고유명사(저자명)와 참고문헌은 PubMed·Crossref 서지로 바로잡는다.
5. 확인 수준에 **"전문 확인(OCR)"**과 **"그림에서 읽은 근사값"**을 추가한다.
6. 도서관 표지·저작권 안내 페이지를 자동으로 걸러낸다.

### 1.6 독립 프로그램 vs MCP 서버 (결정: MCP 우선)

**운영 방식 (확인됨)**: 발표 레지던트가 각자 자기 노트북에서 자료를 준비한다. 프로그램은 개인 사용을 전제로 하고, 공유 기능은 넣지 않는다 (1.7절).

**비교 요약**

| 항목 | 독립 프로그램 | MCP 서버 | 우세 |
|---|---|---|---|
| 구독 계정 활용 | 불가 (API 키 종량 과금 또는 로컬 모델) | 정식 지원 | MCP |
| 개발 비용 | 화면, LLM 연결, 설치 파일, 서명, 업데이트 (수개월) | 엔진에 도구 정의 추가 (수 주) | MCP |
| 결과 일관성 | 코드가 단계와 검증을 강제 | LLM이 순서를 정함 → 설계로 보완 필요 | 독립 |
| 근거 검증 화면 | 원문·주장 나란히 보기 가능 | 대화 중심 → HTML 보고서로 보완 | 독립 |
| 긴 문서 처리 | 분할·요약을 직접 통제 | 대화 용량·구독 사용량 한도 | 독립 |
| 망분리·오프라인 | 로컬 모델로 가능 | 인터넷 필요 | 해당 없음 (개인 노트북은 인터넷 가능) |
| 유지보수 | API·OS 변화에 직접 대응 | AI 앱의 발전을 그대로 활용 | MCP |

병원 망분리가 개인 노트북에 적용되지 않으므로 독립 프로그램의 가장 큰 고유 장점(오프라인 동작)이 이 사용 환경에서는 필요 없다. 남은 독립 프로그램의 장점(일관성, 검증 화면, 긴 문서 통제)은 아래 설계 원칙으로 대부분 보완할 수 있다.

**MCP 서버 설계 원칙**

1. **도구는 단계 단위로 크게 만든다.** `analyze_lineage(project)`, `supplement_methods(project)`처럼 한 단계를 엔진이 정해진 순서로 실행하고, LLM에게는 판단과 서술만 맡긴다. 잘게 쪼갠 도구만 주면 실행마다 단계가 빠지거나 순서가 바뀐다.
2. **상태는 프로젝트 폴더에 둔다.** `project.json`에 단계별 완료 여부, 근거 목록, 확인 수준을 기록하고, 앞 단계가 끝나지 않으면 다음 단계 도구가 실행을 거부한다. 대화가 끊겨도 이어서 할 수 있다.
3. **결과는 파일로 쓰고 대화에는 요약만 돌려준다.** 논문 본문과 참고문헌 전문을 대화에 그대로 넣지 않는다. 대화 용량과 구독 사용량을 아낀다.
4. **인용은 도구만 만든다.** 서지 정보는 PubMed·Crossref 조회 결과로만 채우고, LLM이 쓴 인용은 ID 대조를 통과해야 산출물에 들어간다.
5. **검증은 HTML 보고서로 한다.** 주장-근거 대조표(원문 위치, 확인 수준, 의심 항목)를 브라우저로 열어 확인하게 한다. 지원하는 앱에서는 MCP 화면 확장을 선택적으로 쓴다.
6. **안내 프롬프트를 함께 제공한다.** MCP의 프롬프트 기능으로 "저널클럽 준비 시작" 같은 정해진 시작점을 두어, 레지던트마다 다른 방식으로 시작하지 않게 한다.
7. **마지막에 품질 점검 도구를 둔다.** `check_project`가 빠진 단계, "확인 못 함" 주장 수, 라이선스 불명 그림, 구독 원문 문장 유출을 보고하고, 통과해야 최종 산출물을 만든다.
8. **전송 차단은 서버 코드가 한다.** MCP에서는 도구가 돌려준 내용이 그대로 클라우드 모델로 간다. 따라서 구독 원문(L 등급) 텍스트를 돌려주는 도구는 만들지 않고, 등급에 따라 걸러 내는 일은 AI에게 맡기지 않는다 (1.8절).

**레지던트 직접 준비 방식에서 생기는 문제와 대응**

| 문제 | 대응 |
|---|---|
| **레지던트마다 구독이 필요** (계정 공유는 약관 위반) | 기본 지원 앱 하나를 정하고 필요한 요금제를 안내한다. 구독이 없는 사람을 위한 API 키 CLI 경로를 남겨 둔다 |
| **구독 사용량 한도** | 논문 1편 처리에 드는 사용량을 파일럿에서 측정한다. 원칙 3으로 사용량을 줄이고, 단계마다 나눠 실행할 수 있게 한다 |
| **설치 부담** (Python, OCR 도구, Docling 모델 수백 MB) | Claude Desktop 확장 패키지(.mcpb)처럼 실행 환경을 묶은 설치본을 만든다. Windows에서 Tesseract·Ghostscript 설치가 걸림돌이면 스캔본 OCR은 첫 사용 때 받는 선택 구성요소로 둔다 |
| **레지던트 간 품질 차이** | 원칙 1, 6, 7로 흐름을 고정하고, 읽기 양식(1.8절)으로 확인 항목을 통일한다. 지도교수 검토는 발표 전 단계로 둔다 |
| **AI 앱마다 동작 차이** | 기본 지원 앱 하나에서 평가 세트로 검증하고, 다른 앱은 "동작 가능, 미검증"으로 안내한다 |

**공용 서버 PC 검토 결과 (결정: 만들지 않음)**

| 방안 | 판단 |
|---|---|
| A. 공용 자료 저장소 | 공유 기능 자체를 넣지 않으므로 필요 없음 (1.7절) |
| B. 처리 서버 (OCR, 문서 생성) | 설치 실패가 잦을 때만 도입. 병원 와이파이의 기기 간 통신 차단(AP 격리), IT 승인, 운영 부담 때문 |
| C. 처리 + AI 서버 (기관 API 키) | 레지던트 구독 비용이 부담될 때 Phase 6과 함께 검토. 구독 원문을 서버로 모으는 구조가 되므로 1.8절의 전송 규칙을 다시 검토해야 한다 |

**독립 데스크톱 앱을 다시 검토할 조건** (파일럿 후 판단)

- 구독 비용이 레지던트에게 부담이 되어, 기관 API 키로 일괄 지원하는 편이 낫다고 판단될 때
- HTML 보고서만으로는 근거 검증이 불편하다는 피드백이 많을 때
- 기본 지원 앱의 정책이나 MCP 지원이 크게 바뀔 때

### 1.7 개인 문헌 보관함과 중복 방지 (결정: 개인 사용, 공용 폴더 제외)

**범위 결정**: 프로그램은 개인 사용을 전제로 한다. 논문을 입력하면 학습자료와 발표자료만 만든다. 공용 클라우드 폴더, 공유 묶음 내보내기, 레지던트 간 코퍼스 공유는 넣지 않는다.

- **이유**: 공개 배포 시 가장 위험한 기능이 구독 원문 공유였다. 같은 기관 안에서는 계약 범위일 수 있지만, 다른 기관 사용자와 폴더를 함께 쓰면 곧 계약 위반이 된다. 동기화 충돌, 잠금 파일, 계정 소유권 문제도 함께 사라진다.
- **잃는 것**: 다른 레지던트가 이미 받은 원문과 OCR 결과를 다시 쓰지 못한다. 개인 보관함 안에서의 중복 방지로 일부 보완한다.
- 이전 설계(공용 클라우드 폴더 코퍼스, 2026-10-27)는 저장소 기록(커밋 d7912e7)에 남아 있다.

**폴더 구조** (사용자 노트북, 위치는 설정으로 지정)

```
JournalClubLibrary/                개인 문헌 보관함
├── fulltext/
│   ├── open/                      F 등급 원문 (CC 라이선스 출판본, 저자 원고, 프리프린트)
│   ├── restricted/                L 등급 원문 (구독, 무료 열람, 라이선스 불명)
│   └── scan/                      도서관 스캔본 원본 (L 등급)
├── abstracts/                     PubMed 초록 (PMID별 파일)
├── supplements/                   보충자료
├── derived/                       OCR 결과, Docling 구조 추출, 본문 텍스트
└── records/                       문헌당 기록 파일 1개 (서지, 라이선스 등급과 근거, 보유 파일)
```

작업 중인 프로젝트 폴더(`project.json`, 읽기 양식, 산출물)는 발표 논문별로 따로 둔다.

**중복 판정**

1. DOI(소문자 정규화) → 2. PMID → 3. 제1저자·연도·제목 앞부분 순으로 같은 문헌인지 판정한다.
2. 파일 해시값(SHA-256)으로 이름만 다른 같은 파일을 걸러낸다.
3. 조회·다운로드 전에 `records/`를 먼저 확인하고, 있으면 건너뛰고 "보유 중"으로 표시한다.
4. 초록만 있던 문헌의 원문이 들어오면 추가하고 확인 수준을 "초록 확인 → 전문 확인"으로 올린다.

**중복 OCR 방지**: OCR·Docling 결과는 `derived/`에 **원본 파일 해시값 + 처리 도구 버전**을 이름으로 저장한다. 같은 원본·같은 버전이면 다시 처리하지 않는다 (Löe 1965 기준 11쪽 약 54초 절약).

**다시 받지 않아도 다시 확인할 것**: 철회(retraction)·정정(erratum) 여부와 라이선스는 서지 정보로 주기적으로 다시 확인한다. 철회된 논문은 기록에 표시하고, 이를 근거로 쓴 프로젝트가 있으면 알린다.

### 1.8 구독 원문 전송 문제 (결정: 라이선스 등급 + 읽기 양식)

**문제**: 최근 구독 계약에는 구독 자료를 AI 도구에 올리는 것을 제한하는 조항이 많다. 클라우드 AI가 원문 전체를 읽는 구조는 이 조항과 충돌한다. 한국에는 명시적인 TDM 면책 조항이 없고(2025년 11월 문화체육관광부는 도입 가능성이 낮다고 밝힘), 공정이용(제35조의5)에 기대야 하므로 계약 조건과 보수적인 기본값이 더 중요하다. 아래는 설계 검토이며 법률 자문이 아니다. 공개 전에 도서관과 법률 전문가의 확인을 받는다.

**위험의 세 층**

| 층 | 누구의 행위인가 | 대응 |
|---|---|---|
| ① 배포하는 프로그램 | 개발자 | 논문을 담거나 호스팅하지 않음, 접근 제한 우회 없음(Sci-Hub 연동 등 금지), 대량 자동 다운로드 없음 |
| ② 프로그램으로 하는 일 (원문 받기, 저장, AI 전송) | 사용자 | 기본 설정이 위반으로 이끌지 않게 한다. "사용자 책임" 고지는 보조 수단일 뿐이다 |
| ③ 산출물 (그림, 인용) | 사용자 | 그림 재사용 규칙 (2절 6항) |

**계약 조항의 세 유형** (도서관에 출판사별로 어느 유형인지 확인한다)

| 유형 | 금지하는 것 | 가능한 처리 |
|---|---|---|
| ① 학습 금지 | AI 모델 학습에 쓰는 것 | 학습에 쓰지 않는 요금제·API라면 전문 전송이 가능할 수 있다 |
| ② 제3자 업로드 금지 | 외부 AI 서비스에 올리는 것 | 원문은 노트북 안에서만 처리하고 사실·메모만 보낸다 |
| ③ AI 처리 일체 금지 | 로컬 AI 처리까지 포함 | AI가 아닌 추출 코드, 사람이 읽고 입력, 다른 판본 사용 |

공개판은 기관의 계약을 알 수 없으므로 **기본값은 ②로 가정**한다.

**검토한 방안**

| 방안 | 판단 |
|---|---|
| OA 논문만 허용 | 안전하지만 계보 추적과 방법 보완 대상(오래된 구독 논문)을 크게 잃는다. 판정 단계의 한 갈래로 쓴다 |
| 초록·서지만 사용 | 방법 보완이 불가능하다. 원문이 없을 때의 대체 경로로만 쓴다 |
| 같은 논문의 재이용 가능한 판본 | CC 라이선스 저자 원고·프리프린트를 Unpaywall·PMC로 찾는다. 출판본과 숫자가 다를 수 있어 대조 문항을 둔다. **채택** |
| 추출 코드 (AI 없음) | 참고문헌, 섹션, 용량·단위·기간, 키워드 주변 문장. 사실만 다루므로 안전하다. **채택** |
| 로컬 모델 | 원문이 노트북 밖으로 나가지 않는다. 하드웨어 부담 때문에 **선택 사항**으로 둔다 |
| 사용자가 읽고 입력하는 읽기 양식 | 전송되는 것이 사용자 본인의 메모라 가장 깨끗하다. 시간이 들지만 레지던트가 논문을 직접 읽게 하는 교육 목적과 맞는다. **채택** |
| 출판사 허가 AI 경로 (Wiley의 Claude 연동, GetFTR·Silverchair MCP 등) | MCP 앱에 우리 서버와 출판사 커넥터를 함께 연결하는 구조는 가능하다. 지원 범위가 출판사마다 다르고 대형 출판사 지원은 확인하지 못했다. **장기 관찰** |
| 데이터 보관 없는 AI 서비스 | ② 유형에서는 여전히 제3자 전송이다. 해법이 아니다 |
| 학회 회원 개인 구독, 논문 개별 구매 | 별도 이용 조건이 있고 대개 더 엄격하다. 해법이 아니다 |
| 기관 협상 | 도서관에 요청할 수 있지만 설계가 의존하면 안 된다 |

#### 통합 흐름

모든 논문에 **같은 읽기 양식**을 쓰고, 라이선스 등급에 따라 "누가 초안을 채우는지"와 "무엇을 클라우드로 보내는지"만 달라진다. OA 논문에서도 레지던트가 직접 읽는 단계가 빠지지 않는다.

```
[1 입력] DOI·PMID 또는 PDF
   │
[2 라이선스 판정]  엔진, AI 없음, 노트북 안
   │   전체 등급(F)  /  로컬 등급(L)
   │
[3 원문 준비]  텍스트 추출, 섹션, 참고문헌, OCR  ← 노트북 안
   │
[4 읽기 양식 생성]  논문 유형별 질문 + 이 논문 맞춤 질문
   │
[5 초안 채우기]
   │   F: 클라우드 AI가 전문을 읽고 초안 + 원문 인용
   │   L: 추출 코드(+선택: 로컬 모델)가 초안 + 위치
   │
[6 사용자 확인]  PDF와 양식을 나란히 놓고 확인·수정
   │   핵심 문항은 "먼저 답하고 나중에 비교"
   │
[7 전송 게이트]  MCP 서버가 등급별로 보낼 내용을 만들고 미리보기
   │   F: 전문 + 확인된 양식
   │   L: 확인된 양식(사실·메모) + 서지 + 초록
   │
[8 산출물 작성]  클라우드 AI가 학습자료·발표자료 작성
   │
[9 check_project]  확인 여부, 출처 추적, 구독 원문 문장 유출 검사
   │
[10 빌드]  PDF·슬라이드  ← 노트북 안
```

참고문헌 논문(계보, 방법 보완)도 2-6단계를 **논문별로 따로** 거친다. 한 프로젝트 안에서 대상 논문은 F, 참고문헌 21번은 L처럼 등급이 섞일 수 있다. 대상 논문은 전체 내용과 비평이 필요하고, 참고문헌 논문은 용량·품종·기간 같은 작은 사실 몇 개만 필요하므로 L 등급의 손실은 참고문헌 쪽에서 작다.

**2단계: 라이선스 판정**

- 조회처: PMC(라이선스 필드), Europe PMC, Unpaywall(판본, 라이선스), Crossref(라이선스 URL). 정보가 없으면(국내 학술지 등) 논문 페이지의 저작권 표시를 읽고, 그래도 없으면 사용자가 입력한다.

| 상황 | 등급 | 전송에 쓰는 파일 |
|---|---|---|
| CC 라이선스 (BY, BY-NC, ND 포함, CC0) | F | 사용자 PDF 또는 OA 판본. 라이선스는 논문 자체에 붙으므로 어느 쪽이든 가능 |
| CC 라이선스가 붙은 저자 원고나 프리프린트만 있음 | F | **그 판본 파일만** (엔진이 직접 받아옴). 사용자가 가진 출판본 PDF는 보내지 않음 |
| PMC 저자 원고 (CC 없음) | L (기본, 권장안) | 설정으로 F 허용 가능 |
| 구독, 무료 열람(bronze), 정보 없음 | L | 없음 |
| 조회처끼리 판정이 다름, 조회 실패 | L | 없음. 불확실하면 막는 쪽 |

- **판정 근거 기록**: `project.json`과 문헌 기록 파일에 조회처, 라이선스 URL, 판본, 확인 날짜를 남긴다.
- **등급 올리기**: L을 F로 바꾸려면 "기관 계약이 ① 학습 금지형"이라는 설정과 도서관 확인 날짜를 입력해야 한다. 이 변경도 기록한다. 공개판이 특정 기관의 계약 해석을 대신 정하지 않는다.

**4단계: 읽기 양식 생성**

- 공통 질문: 논문 유형별 점검표(ARRIVE, CONSORT 등, 1.1절)에서 가져온다.
- 맞춤 질문: 이 논문에서 확인할 것. 예: "JEL은 어떻게 정의했는가", "마취 용량의 근거 문헌은 무엇인가", "ref 30에 BCL 측정이 있는가".
  - F: 클라우드 AI가 전문을 보고 만든다.
  - L: 클라우드 AI는 초록, 서지, 참고문헌 목록, 섹션 제목, 추출 코드가 찾은 사실만 보고 만든다.
- 문항 형식: 문항 번호, 질문, 답 형식(숫자+단위 / 선택지 / 짧은 서술), 필수 여부, 근거 위치(쪽, 단락).

**5단계: 초안 채우기**

- F: 클라우드 AI가 초안과 원문 인용·위치를 쓰고, 엔진이 인용이 원문에 실제로 있는지 글자 단위로 대조한다.
- L: 추출 코드가 후보 문장의 위치를 찾고 용량·기간·품종 같은 값을 채운다. 로컬 모델이 있으면 서술형 문항도 초안을 쓴다.
- 문항 상태: 초안(AI) / 초안(코드) / 확인 / 수정 / 원문에 없음 / 미확인.

**6단계: 사용자 확인 (읽기 양식 화면)**

- MCP 서버가 노트북에서 **로컬 웹페이지**를 연다(권장안). 왼쪽은 PDF, 오른쪽은 양식. 문항을 누르면 근거 위치로 이동해 강조한다.
- **"먼저 답하기" 문항**: 연구 질문, 주요 결과, 가장 큰 약점 같은 핵심 3-5개(권장안)는 초안을 숨기고, 사용자가 먼저 답한 뒤 AI 초안과 비교한다. 초안을 그대로 승인만 하는 것을 막고 교육 효과를 얻는다.
- 필수 문항은 모두 확인하거나 "원문에 없음"으로 표시해야 다음 단계로 간다.
- 저자 원고를 쓴 경우 "핵심 숫자를 출판본과 대조했는가" 문항이 자동으로 추가된다.
- 사용자에게 PDF가 없는 참고문헌은 초록 기준으로 처리하고 "미확인"으로 남긴다.

**7단계: 전송 게이트 (MCP 서버가 강제)**

| 보내는 것 | F | L |
|---|---|---|
| 서지, 초록, 참고문헌 목록 | 보냄 | 보냄 |
| 확인된 양식 답 (사실, 메모) | 보냄 | 보냄 |
| 원문 인용 | 보냄 | 기본 차단(권장안). 기관 설정으로 짧은 인용 허용 가능 |
| 전문 | 보냄 | 차단 |
| 그림 | CC 그림은 출처 표시 후 사용 | 차단 |

- 전송 직전에 보낼 내용 미리보기를 보여 주고, 무엇을 언제 보냈는지 `project.json`에 기록한다.
- L 등급 원문 텍스트를 돌려주는 도구는 만들지 않는다(1.6절 원칙 8).
- 사용자 메모에 원문을 복사해 넣은 경우를 잡기 위해, 전송 직전에 L 등급 원문과 메모를 연속 단어 단위로 대조한다.

**8-9단계: 작성과 검사**

- 산출물의 각 주장에 확인 수준을 붙인다: [FT] 전문 확인, **[U] 사용자 확인 (신규)**, [A] 초록 확인, [R] 서지 확인.
- 그림: F 등급은 CC 그림을 출처와 함께 사용한다. L 등급은 "Fig. 2, Kim 2024 (see original)" 자리 표시만 넣거나, 사용자가 입력한 숫자로 다시 그린다.
- `check_project`: 필수 문항 확인, 모든 주장의 출처 추적, 식별자 검증, 과장 표현, **L 등급 원문 문장의 산출물 유출**(노트북 안에서 연속 단어 대조).
- 산출물에 처리 모드를 표시하고, L 등급 결과는 "원문 일부 미확인" 항목을 함께 보여 준다.

**F 등급과 L 등급 비교**

| | F (전문 전송) | L (로컬) |
|---|---|---|
| 초안 작성자 | 클라우드 AI | 추출 코드 (+로컬 모델) |
| 사용자 역할 | 초안 확인, 핵심 문항 직접 답 | 확인할 문항이 더 많고 서술형은 직접 작성 |
| 산출물 품질 | 기준 결과 수준 | 사용자 확인 범위에 따라 달라짐 (측정 필요) |
| 사용자 시간 | 짧음 | 김 (측정 필요) |

**MCP 도구 구성 (안)**

| 도구 | 하는 일 | 클라우드로 가는 것 |
|---|---|---|
| `check_license` | 2단계 판정과 근거 기록 | 등급과 근거 요약 |
| `prepare_source` | 3단계 원문 준비 | 섹션 제목, 추출된 사실 |
| `build_form` | 4단계 양식 생성 | 양식 구조 |
| `get_fulltext` | F 등급에서만 동작 | 전문 |
| `open_reading_form` | 6단계 화면 열기 | 없음 |
| `get_confirmed_notes` | 7단계 전송 묶음 생성 | 등급에 맞게 걸러진 내용 |
| `check_project`, `build_outputs` | 9-10단계 | 검사 요약 |

**결정 전에 측정할 것**

1. **OA 비율**: 지난 1-2년 저널클럽 논문 10-20편을 DOI로 판정해, 대상 논문과 참고문헌 각각 F 등급 비율을 센다. 대부분 F라면 L 경로는 보조 기능으로 충분하고, 그렇지 않으면 읽기 양식이 이 프로그램의 중심 기능이 된다.
2. **L 경로 품질과 시간**: jpis-56-189를 L 등급으로 가정하고 추출 코드 + 읽기 양식만으로 만든 결과를 F 기준 결과와 비교한다.

**공개 배포 시 지킬 것**

- 저장소의 시험용 논문, 예시 산출물, 테스트 데이터는 CC BY 논문으로만 만든다. `input/`, `output/`은 계속 git에서 제외한다.
- 원문 수집은 PMC, Europe PMC, Unpaywall 등의 공식 API만 쓰고 요청 빈도 규정을 지킨다. PMC는 승인된 경로 밖의 체계적 자동 수집을 금지한다.
- 첫 실행 때 기관 정책(계약 유형)을 묻고, 기본값은 가장 보수적인 설정으로 둔다.

## 2. 새로 추가할 사항

1. **근거 추적 (가장 중요)**
   모든 문장 단위 주장에 [출처 문헌 ID, 원문 위치(쪽·문단), 확인 수준]을 저장한다. 산출물에서 확인 수준을 표시하고, 원문을 확인하지 못한 주장은 눈에 띄게 구분한다. 확인 수준에 "사용자 확인 [U]"를 추가한다 (1.8절).

2. **사람 검토 단계**
   - 읽기 양식(1.8절 6단계)에서 발표자가 원문을 보며 핵심 문항을 직접 답하고 초안을 확인한다.
   - ①②③ 각 단계 결과는 편집 가능한 문서(마크다운)로 먼저 보여 주고, 지도교수나 발표자가 고친 뒤에 PDF와 슬라이드를 만든다. 자동 생성 결과를 그대로 발표하지 않게 한다.

3. **평가용 논문 세트와 품질 기준**
   유형별 3-5편(총 15-20편)을 골라 기대 산출물의 기준을 정한다. 예: "생략된 방법 항목을 몇 개 찾았나", "인용 오류를 찾았나", "만들어 낸 인용이 0건인가". 프롬프트나 모델을 바꿀 때마다 이 세트로 다시 점검한다. 첫 사례(jpis-56-189)가 첫 기준 자료다.

4. **기관 양식 지원**
   병원·학교의 PowerPoint 템플릿(.potx)과 PDF 양식을 불러와 쓸 수 있게 한다.

5. **산출물 언어: 영어 단일 (결정)**
   원문 논문과 같은 언어로 자료를 만든다. 번역 단계가 없어 숫자·표현이 바뀔 위험이 사라지고, 로컬 모델도 영어에서 더 정확했다(1.3절 4항). 발표자 노트는 만들지 않는다. 토론은 세미나에서 한국어로 한다. 영어 단일의 약점은 다음 규칙으로 보완한다.
   - **쉬운 영어 작성 규칙**: 짧은 문장, 문장 하나에 주장 하나, 약어는 처음 나올 때 풀어 쓰기.
   - **확인 수준별 표현 규칙**: 확인 수준에 따라 쓸 수 있는 동사를 정한다(예: 전문 확인 "states", 초록 확인 "reports (abstract)", 추정 "may suggest"). 레지던트가 확신의 정도를 놓치지 않게 한다.
   - **과장 표현 검사**: "proves", "clearly demonstrates" 같은 표현이 낮은 확인 수준과 함께 쓰이면 자동으로 표시한다.
   - **언어 혼입 검사**: 결과 파일에 한글·한자 등 영어 외 문자가 섞였는지 자동으로 검사한다. 모든 지시문에 출력 언어를 명시해 AI 앱·하네스의 기본 언어 설정과 충돌하지 않게 한다.
   - 한국어로만 있는 자료(국내 지침, KCI 논문)는 입력으로 받되, 정리는 영어로 하고 출처에 "Korean-language source"로 표시한다.

6. **저작권 기준**
   - 원문 전송은 라이선스 등급을 따른다 (1.8절).
   - 그림: CC 라이선스 그림만 자동으로 넣고 라이선스와 출처를 단다. ND 라이선스 그림은 수정하지 않는다. 나머지는 "Fig. N, 저자 연도 (see original)"로 대체하거나 보고된 숫자로 다시 그린다. 인용(저작권법 제28조)은 정당한 범위 안에서만 인정되고, 학교교육 조항(제25조)이 병원 수련교육에 적용되는지는 불분명하므로 보수적으로 둔다.

7. **발표 이력과 지식 누적 (개인)**
   발표한 논문, 정리한 연구 흐름, 확인한 문헌을 개인 보관함에 쌓아서 다음 논문 정리에 다시 쓴다. 같은 연구팀의 후속 논문이나 같은 주제가 나오면 이전 기록을 연결한다.

## 4. 단계별 로드맵

기간은 1인 개발 기준의 대략적인 추정이다.

### Phase 0. 기반 정리 (1-2주)

- [ ] 요구사항과 이 로드맵 확정 (8절의 결정 사항)
- [ ] 평가용 논문 세트 선정: 유형별 3-5편
- [ ] 첫 사례(jpis-56-189)를 기준 자료로 정리
- [ ] OA 비율 측정: 지난 1-2년 저널클럽 논문 10-20편과 그 참고문헌의 라이선스 등급 (1.8절)
- [ ] 도서관 질문: 출판사별 계약 조항 유형(학습 금지 / 제3자 업로드 금지 / AI 처리 일체 금지)
- [ ] 기술 결정 기록(ADR) 작성: 언어, MCP 우선 구조(1.6절), 개인 사용 범위(1.7절), 라이선스 등급(1.8절), 기본 지원 AI 앱
- [ ] 저장소 기본 설정: 폴더 구조, 테스트, 코드 스타일, 라이선스

**완료 기준**: 평가 세트와 품질 기준표가 있고, 기술 결정이 문서로 남아 있다.

### Phase 1. 처리 엔진 핵심 (4-6주)

- [ ] PDF 해석: 본문 섹션, 그림·표 위치, 참고문헌 목록 추출 (PyMuPDF, 선택적으로 GROBID)
- [ ] 스캔본 처리: 텍스트 층 확인 → OCRmyPDF → Docling 구조 정리, 숫자·표 이중 판독(OCR + 이미지 LLM 또는 RapidOCR), 표 내부 일관성 검사 (1.5절)
- [ ] 참고문헌 → DOI/PMID 매칭 (Crossref, PubMed)
- [ ] 문헌 조회 모듈: PubMed, Europe PMC, Crossref, OpenAlex, Unpaywall
- [ ] 프로젝트 폴더 구조와 `project.json` (단계 상태, 근거 목록, 확인 수준)
- [ ] 개인 문헌 보관함 (1.7절): 등급별 폴더 분리, 문헌당 기록 파일, DOI/PMID/해시 중복 판정, OCR 결과 재사용
- [ ] 라이선스 판정 모듈 (1.8절 2단계): PMC, Europe PMC, Unpaywall, Crossref 조회, F/L 등급, 판정 근거 기록, 불확실하면 L
- [ ] 같은 논문의 재이용 가능한 판본 찾기: CC 라이선스 저자 원고, 프리프린트
- [ ] 추출 코드: 용량·단위·기간·품종, 키워드 주변 문장, 근거 위치(쪽, 단락)
- [ ] 근거 추적 데이터 구조와 확인 수준 표시 ([FT], [U], [A], [R])
- [ ] 논문 유형 판별 (출판 유형 정보 + LLM + 사용자 확인)
- [ ] 자동 검사: 서지 ID 대조(PMID·PMC·인용 번호), 1·2단계 사이 일관성, 과장 표현, 언어 혼입 (2절 5항), L 등급 원문 문장 유출 (연속 단어 대조)
- [ ] 로컬 모델 평가: 평가 세트로 원문 대조·추출 품질과 처리 시간 측정 (1.3절 4항)
- [ ] CLI: 엔진 시험과 평가 세트 실행용 (`jca analyze paper.pdf`)

**완료 기준**: 엔진 도구들이 평가 세트의 Original article에서 첫 사례와 같은 근거 자료(전작 방법, 인용 대조)를 찾아 프로젝트 폴더에 기록한다.

### Phase 2. MCP 서버 (3-4주)

- [ ] 단계 단위 도구: 프로젝트 시작, 유형 확인, ① 맥락, ② 보강·검증, ③ 결과 해석, 산출물 생성, 품질 점검 (1.6절 원칙 1-8)
- [ ] 라이선스·전송 도구: `check_license`, `prepare_source`, `build_form`, `get_fulltext`(F 등급만), `get_confirmed_notes` (1.8절)
- [ ] 전송 게이트: 등급별 전송 내용 생성, 미리보기, 전송 기록
- [ ] 읽기 양식 화면 (로컬 웹페이지): PDF와 양식 나란히 보기, 근거 위치 이동, "먼저 답하기" 문항, 필수 문항 확인
- [ ] 안내 프롬프트: "저널클럽 준비 시작"
- [ ] 근거 대조 HTML 보고서
- [ ] 설치 패키지(.mcpb 등): Windows, macOS 개인 노트북. 스캔본 OCR은 선택 구성요소
- [ ] 레지던트용 설치·사용 안내 (1쪽)
- [ ] 논문 1편당 구독 사용량 측정

**완료 기준**: 레지던트 1명이 안내서만 보고 자기 노트북에 설치해 Original article 1편을 처리하고, 만들어 낸 인용이 0건이다. L 등급 문헌의 원문 텍스트가 클라우드로 전송된 기록이 0건이다.

### Phase 3. 유형별 처리와 산출물 (4-6주)

- [ ] Original article 하위 유형별 점검표와 읽기 양식 문항 세트 (RCT, 관찰, 동물, 진단). 첫 양식은 jpis-56-189로 동물실험용을 만든다
- [ ] L 경로 품질·시간 측정: jpis-56-189를 L 등급으로 가정해 F 기준 결과와 비교 (1.8절)
- [ ] SR/MA 처리: PRISMA/AMSTAR 2 점검, 보충자료 입력, 포함 연구 표, GRADE 정리
- [ ] Narrative review 처리: 주장-근거 대응표, SANRA 점검
- [ ] 산출물 생성: 학습용 PDF, PowerPoint 슬라이드(영어, 발표자 노트 없음), 기관 템플릿 적용
- [ ] 그림 추출과 라이선스·출처 표시. L 등급은 자리 표시 또는 숫자로 다시 그리기 (2절 6항)

**완료 기준**: 세 유형 평가 세트 전체에 대해 PDF와 슬라이드가 생성되고, 지도교수 검토 점수가 기준을 넘는다.

### Phase 4. 원문 접근과 개인 보관함 (2-3주)

- [ ] 기관 프록시 링크 설정 (병원 밖 사용 시, 기관별로 한 번)
- [ ] "필요한 원문" 목록 (HTML): DOI / 프록시 / PubMed 링크, "병원 와이파이에서 열기" 안내
- [ ] 다운로드 폴더 감시 → DOI로 짝짓기 → 개인 보관함에 추가 (등급 판정 포함)
- [ ] 오픈 액세스 원문 자동 수집 (Unpaywall, Europe PMC)
- [ ] 원문을 받은 뒤 확인 수준 자동 갱신 (초록 확인 → 전문 확인)

## 7. 첫 사례에서 얻은 교훈 (설계에 반영)

1. **인용을 실제로 열어 봐야 가치가 생긴다.** ref 29와 ref 30의 문제는 원문 대조로만 찾을 수 있었다. → 근거 추적과 원문 대조가 핵심 기능이다.
2. **전작(같은 연구팀의 이전 논문)이 가장 중요한 보강 자료다.** → 저자·연구팀 기준 문헌 탐색을 기본 기능으로 넣는다.
3. **방법 보강에는 계산과 환산이 자주 필요하다.** (용량 계산, 마취제 mg/kg 환산) → 가정을 명시한 계산 결과를 별도로 표시한다.
4. **PDF와 슬라이드는 사용자 PC 글꼴에 따라 모양이 달라진다.** → 글꼴 내장(PDF)과 기본 글꼴 선택(PowerPoint)을 설정으로 둔다. 산출물을 영어 단일로 정해 한국어 글꼴 문제는 줄었다.
5. **결과물 검토에 시간이 든다.** → 미리보기 화면과 단계별 편집이 필요하다.
