## 1. 요구사항별 비판적 검토

### 1.1 논문 유형별 처리

**동의하는 점**: 유형마다 구성과 읽는 법이 다르다. 같은 3단계를 모든 논문에 적용하면 체계적 문헌고찰에서는 "선행연구 흐름 정리"가 논문 본문과 겹치고, 종설(narrative review)에서는 "방법 보강"할 대상이 거의 없다.

**보완할 점**

1. **유형을 더 나눠야 한다.** "Original article" 안에서도 설계마다 확인할 내용이 다르다.

   | 유형 | 보고 지침 (구성 확인용) | 비뚤림·질 평가 도구 |
   |---|---|---|
   | 무작위 임상시험(RCT) | CONSORT | RoB 2 |
   | 관찰연구 (코호트, 환자-대조군, 단면) | STROBE | ROBINS-I / ROBINS-E, NOS |
   | 진단 정확도 연구 | STARD | QUADAS-2 |
   | 동물실험 (첫 사례) | ARRIVE 2.0 | SYRCLE RoB |
   | 체계적 문헌고찰 / 메타분석 | PRISMA 2020 | AMSTAR 2, ROBIS |
   | 종설 (narrative review) | SANRA | SANRA |
   | 증례보고 / 증례군 | CARE | JBI 체크리스트 |
   | 진료지침 / 합의문 | RIGHT | AGREE II |
   | 시험관 연구 (in vitro) | (표준 지침 약함) | 자체 체크리스트 |

2. **3단계를 유형별로 다시 정의한다.**

   | 단계 | Original article | SR / MA | Narrative review |
   |---|---|---|---|
   | ① 맥락 | 선행연구 흐름, 연구팀 계보 | 이 리뷰 이전의 리뷰들과의 관계, 이 리뷰가 메우는 공백 | 리뷰가 다루는 분야의 지도, 저자의 관점과 이해상충 |
   | ② 보강·검증 | 생략된 방법을 인용 문헌에서 보강, 인용 정확성 점검 | 프로토콜(PROSPERO), 검색식, 포함·제외 연구 목록, 보충자료에서 빠진 내용 보강, 포함 연구 몇 편의 원문 대조 | 핵심 주장마다 인용한 1차 연구가 실제로 그 주장을 지지하는지 점검, 빠진 주요 연구 탐색 |
   | ③ 결과 해석 | 효과 크기, 통계, 한계 | 숲 그림(forest plot) 다시 읽기, 이질성, 출판 비뚤림, GRADE 근거 수준 | 주장-근거 대응표, 근거 수준별 정리 |
   | 산출물 | 학습 PDF + 발표 슬라이드 | 같음 + 포함 연구 요약표 | 같음 + 주장-근거 지도 |

3. **유형 판별은 자동 + 사용자 확인으로 한다.** PubMed의 출판 유형(Publication Type) 정보를 먼저 쓰고, 없으면 LLM이 판별한 뒤 사용자가 확인한다. 잘못 판별하면 이후 전 과정이 틀어지므로 확인 단계를 생략하지 않는다.

4. **보충자료(supplementary material)를 입력으로 받아야 한다.** 특히 SR/MA는 검색식과 포함 연구 표가 보충자료에 있는 경우가 많다. 본문 PDF만으로는 2단계가 부실해진다.

### 1.2 Windows / Mac 프로그램

**동의하는 점**: 대상 사용자(교수, 레지던트)는 명령줄보다 설치형 프로그램이 익숙하다.

**문제점과 수정**

1. **엔진 먼저, 앱은 나중에.** PDF 해석, 문헌 조회, LLM 호출, 산출물 생성은 화면과 무관한 부분이고 가장 어렵다. 이것을 Python 라이브러리 + CLI로 먼저 완성하고 평가한 뒤 앱을 씌운다. 그래야 화면을 고치느라 핵심 품질 개선이 밀리지 않는다.

2. **기술 선택 (권장안)**

   | 부분 | 권장 | 이유 |
   |---|---|---|
   | 엔진 | Python | PDF·과학 문헌 처리 도구(PyMuPDF, GROBID 연동), 문서 생성(python-pptx, 보고서 PDF)이 가장 풍부 |
   | 데스크톱 셸 | Tauri 2 (+ Python 엔진을 함께 묶어 실행) | Electron보다 설치 파일이 작고 메모리를 적게 씀. 대안: Electron(자료가 더 많음), PySide6(Python만으로 가능하나 화면 품질이 떨어짐) |
   | 화면 | 웹 기술 (React 등) | 중간 결과(마크다운)를 보고 고치는 편집 화면이 필요 |
   | 로컬 저장 | SQLite + 파일 폴더 | 코퍼스, 메타데이터, 작업 이력 |

3. **배포에 드는 비용과 절차를 미리 계획한다.**
   - **macOS**: Apple Developer 계정(연 99달러)으로 서명과 공증(notarization)을 하지 않으면 "확인되지 않은 개발자" 경고로 실행이 막힌다.
   - **Windows**: 코드 서명 인증서가 없으면 SmartScreen 경고가 뜬다. 병원 PC는 서명 없는 프로그램 설치를 막는 경우가 많다.
   - **자동 업데이트**: 처음부터 넣어야 나중에 배포가 편하다.

4. **병원 PC 환경을 고려한다.**
   - **사용 환경 (확인됨)**: 업무용 PC는 EMR/OCS/PACS 망으로 분리되어 있고, 개인 PC·노트북은 인터넷이 되는 별도 와이파이를 쓴다. 따라서 **대상은 레지던트의 개인 노트북(Windows/Mac)**이며 업무용 PC 설치와 완전 오프라인 모드는 고려하지 않는다.
   - **관리자 권한**: 개인 노트북이므로 큰 제약은 아니지만, 사용자 폴더 설치를 기본으로 한다.

### 1.3 LLM 연결 방식

**동의하는 점**: 사용자마다 쓸 수 있는 LLM이 다르므로 여러 방식을 지원해야 한다.

**문제점과 수정**

1. **구독 계정(ChatGPT Plus, Claude Pro 등) 직접 연결은 빼는 것을 권장한다.**
   - 소비자용 구독은 원칙적으로 해당 회사의 앱 안에서 쓰도록 되어 있고, API 사용권을 포함하지 않는다.
   - 제3자 프로그램이 구독 계정으로 로그인해 모델을 호출하는 것은 대부분 약관상 허용되지 않거나 별도 승인이 필요하다. 비공식 방법으로 구현하면 계정 정지 위험이 있고, 언제든 막힐 수 있다.
   - 정책은 자주 바뀌므로, 구현 시점에 각 회사의 최신 약관을 다시 확인한다.

2. **기본 경로: MCP 서버로 구독 사용자를 지원한다.**
   - 이 프로그램의 기능(PDF 해석, PubMed 조회, 인용 대조, 슬라이드 생성)을 MCP(Model Context Protocol) 서버로 제공한다.
   - 사용자는 Claude Desktop 같은 공식 앱에 이 서버를 연결하고, 자기 구독으로 대화하듯 작업한다. 약관 문제 없이 구독을 활용하는 정식 경로다.
   - 이번 첫 사례도 사실상 이 방식(구독 기반 에이전트 + 도구)으로 만들어졌다.
   - 설계 원칙은 1.6절.

3. **API 키 연결 (보조, CLI와 조건부 데스크톱 앱용)**: Anthropic, OpenAI, Google을 우선 지원한다.
   - 키는 OS 보안 저장소(Windows 자격 증명 관리자, macOS 키체인)에 저장하고 파일에 평문으로 두지 않는다.
   - 작업 전에 예상 비용을 보여 준다(논문 1편 처리에 수십만 토큰이 들 수 있음).
   - 반복되는 긴 입력(논문 본문)에는 프롬프트 캐싱을 써서 비용을 줄인다.

4. **로컬 모델**: Ollama, LM Studio 같은 OpenAI 호환 서버로 연결한다.
   - 한계를 정직하게 안내한다. 일반 노트북의 로컬 모델은 긴 논문(수만 토큰)을 다루기 어렵고, 의학 추론과 한국어 품질이 클라우드 모델보다 낮다.
   - 권장 구성: 로컬 모델은 분류, 추출 같은 가벼운 작업에, 클라우드 모델은 종합과 비판적 평가에 쓰는 **작업별 모델 배정**을 지원한다.

5. **모델 종류와 무관하게 지킬 원칙**
   - **LLM은 참고문헌을 만들어 내지 않는다.** 모든 인용은 PubMed, Crossref, OpenAlex에서 조회한 실제 문헌 ID(PMID, DOI)에 연결된 것만 쓴다.
   - **모든 주장에 출처 문장과 확인 수준을 붙인다**: 전문 확인 / 초록 확인 / 2차 자료 / 확인 못 함 (첫 사례의 표기 방식).
   - 출력은 정해진 구조(JSON 스키마)로 받아 검증한다.

### 1.4 원문 접근

**동의하는 점**: 기관 구독으로 최근 논문 원문을 볼 수 있고, 원문이 있어야 2단계(방법 보강)가 제대로 된다.

**문제점과 수정**

1. **프로그램이 자동으로 원문을 대량 다운로드하는 기능은 넣지 않는다.**
   - 출판사와 기관의 계약은 대부분 자동·대량 다운로드를 금지한다. 이를 어기면 **기관 전체의 접근이 차단**될 수 있다.
   - 텍스트·데이터 마이닝(TDM)은 출판사가 제공하는 별도 API와 등록 절차로만 허용되는 경우가 많다.

2. **대신 "사용자가 직접 받도록 돕는" 흐름을 만든다.**
   - **기관 인증 방식 (확인됨)**: 출판사 구독은 병원 인터넷 와이파이의 **IP 기반 인증**이다. 병원 와이파이에 연결된 노트북에서는 DOI 링크만으로 원문이 열린다. 병원 밖(집 등)에서는 도서관 프록시나 VPN이 필요하므로, 링크 화면에 "병원 와이파이에서 열기" 안내를 함께 표시한다.
   - MCP 서버는 사용자 노트북에서 실행되므로 요청은 그 노트북의 IP에서 나간다. 그러나 **프로그램이 출판사 사이트에서 직접 PDF를 받는 기능은 여전히 넣지 않는다.** 병원 IP 전체가 출판사에서 차단되면 모든 구성원이 피해를 입는다.

   1. PDF의 참고문헌을 구조화하고 DOI, PMID를 찾는다.
   2. 각 문헌에 대해 링크를 만든다: DOI 링크(병원 와이파이에서는 이것으로 충분), **기관 프록시 링크**(병원 밖 사용 시, 기관별로 한 번 설정), PubMed 링크.
   3. 사용자가 클릭하면 **평소 쓰는 브라우저**에서 열리고, 기관 인증도 브라우저가 처리한다.
   4. 사용자가 PDF를 내려받으면, 프로그램이 다운로드 폴더를 감시하다가 DOI로 해당 문헌과 짝지어 코퍼스에 넣는다.
   5. 아직 원문이 없는 문헌은 "초록 기준"으로 표시하고, 필요한 문헌 목록을 보여 준다.

3. **오픈 액세스 원문은 공식 API로 직접 가져온다.**
   - Unpaywall: DOI로 합법적인 무료 원문 위치 조회
   - Europe PMC / PubMed Central OA: 구조화된 전문(XML). 첫 사례에서도 이 경로로 전작의 측정 방법을 확인했다
   - OpenAlex, Crossref, Semantic Scholar: 메타데이터, 인용 관계

4. **10년이 넘은 문헌을 고려한다.** 연구 흐름의 뿌리는 오래된 논문인 경우가 많다(첫 사례: 1981, 1983, 1991년 문헌). 도서관에서 스캔본 PDF로 받을 수 있으므로 스캔본 처리를 지원한다(1.5절). 구할 수 없으면 초록으로 처리하고 그렇게 표시한다.

### 1.5 스캔본 PDF (클래식 논문)

도서관이 보내 주는 스캔본으로 시험했다 (Löe, Theilade, Jensen. Experimental Gingivitis in Man. J Periodontol 1965, 11쪽, 600 dpi 흑백).

**시험 결과**

| 항목 | 결과 |
|---|---|
| 텍스트 층 | 출판사가 디지털화하며 넣은 OCR 텍스트 층이 이미 있었음. 오래된 논문도 출판사 사이트에서 받은 PDF는 이런 경우가 많다 |
| 본문 단어 | 기존 텍스트 층과 Tesseract 5 결과를 비교하면 약 4,900단어 중 2.9%가 다름. 대부분 줄 끝 하이픈과 대소문자 차이로 의미 없는 차이 |
| 의미 있는 오류 | 움라우트가 있는 이름 깨짐(Löe → "L e", Mühlemann → "M hlemann"), 숫자 분리("1950" → "19 50"), 'the' → 'trie', 'GI' → 'Gl', 범위 표기 하이픈 누락("0.1 - 1.0" → "0.1 1.0"), 두 단 편집에서 일부 읽는 순서 섞임 |
| 표 숫자 | 표 1, 4의 숫자 78개는 두 방식 모두 정확 |
| 그래프 (그림 2-4) | 막대·영역 모양이라 OCR로는 값을 얻을 수 없음 → 이미지 LLM으로 설명하고 "그림에서 읽은 근사값"으로 표시 |
| 표 자동 검증 | 각 행의 평균을 다시 계산해 표기값과 비교. 6행 중 1행 불일치(표 1, 계산 1.679 vs 표기 1.67) → 이미지 확인 결과 **OCR이 아니라 원문 자체의 값**. 자동 검증은 "다시 볼 곳"을 찾아 주고, 원인 판정은 사람이 한다 |

**Docling 비교 시험 (CPU 4코어, 11쪽)**

텍스트 층을 지운 "이미지만 있는 PDF"를 만들어 도서관 스캔본과 같은 조건에서 비교했다. 기준값은 고해상도 이미지로 확인한 표 숫자 165개.

| 방식 | 시간 | 표 숫자 165개 중 오류 | 본문 점검 10항목 | 비고 |
|---|---|---|---|---|
| 출판사 텍스트 층 + Docling | 58초 | 1 ("1.19" → "1-19") | 9 | 출판사 텍스트 층도 틀릴 수 있음. 그림 1 캡션 없음 |
| 이미지만 + Docling 내장 Tesseract | 87초 | 115 | 6 | 표를 칸 단위로 잘라 읽어 숫자 대부분 손상 ("0.54" → "OM") |
| 이미지만 + Docling 내장 RapidOCR | 98초 | 4 | 8 | 칸 병합 오류, 0.53 → "03", 단어 사이 공백 누락 |
| **이미지만 → OCRmyPDF → Docling** | **13초 + 41초** | **1** ("0.15" → "06.15", 평균 검사로 검출) | **8** | **가장 좋음**. 첫 글자 장식(drop cap) 누락, 움라우트 일부 누락 |

- Docling은 텍스트 층이 있을 때 두 단 편집의 읽는 순서와 범위 하이픈("0.1 - 1.0")을 단순 텍스트 추출보다 잘 복원했다.
- Docling 안에서 OCR을 돌리는 것보다, **OCRmyPDF로 페이지 전체 텍스트 층을 먼저 만들고 Docling은 구조 정리만 맡기는 것**이 빠르고 정확했다.
- 어떤 방식도 숫자 오류가 0은 아니었다. 표 일관성 검사와 두 번째 판독이 반드시 필요하다.

**설계 반영**

1. 텍스트 층 유무를 먼저 확인한다. 없으면 OCRmyPDF(Tesseract 기반)로 텍스트 층을 만든다. 있어도 품질 점수가 낮으면 다시 OCR한다.
2. **숫자·단위·표·그래프는 두 경로로 읽는다**: OCR 텍스트와 이미지 LLM. 결과가 다르면 원본 이미지 조각과 나란히 보여 주고 사용자가 확정한다.
3. **표 내부 일관성 검사**를 자동으로 한다: 평균·합계·백분율 재계산, n 합계, 범위 확인. 불일치는 "OCR 오류 의심"과 "원문 자체 불일치"를 구분해 기록한다.
4. 고유명사(저자명)와 참고문헌은 PubMed·Crossref 서지로 바로잡는다.
5. 확인 수준에 **"전문 확인(OCR)"**과 **"그림에서 읽은 근사값"**을 추가한다.
6. 도서관 표지·저작권 안내 페이지를 자동으로 걸러낸다.

5. **코퍼스 공유에 주의한다.** 받은 PDF는 받은 사람의 개인 학습용이다. 레지던트끼리 코퍼스를 공유하는 기능은 기관 계약을 확인하기 전까지 넣지 않는다. 대신 메타데이터, 요약, 주장-근거 기록(원문 아님)은 공유할 수 있게 한다.

### 1.6 독립 프로그램 vs MCP 서버 (결정: MCP 우선)

**운영 방식 (확인됨)**: 발표 레지던트가 각자 자기 노트북에서 자료를 준비하고, 결과물을 공용 클라우드 폴더에 올려 공유한다.

**비교 요약**

| 항목 | 독립 프로그램 | MCP 서버 | 우세 |
|---|---|---|---|
| 구독 계정 활용 | 불가 (API 키 종량 과금 또는 로컬 모델) | 정식 지원 | MCP |
| 개발 비용 | 화면, LLM 연결, 설치 파일, 서명, 업데이트 (수개월) | 엔진에 도구 정의 추가 (수 주) | MCP |
| 결과 일관성 | 코드가 단계와 검증을 강제 | LLM이 순서를 정함 → 설계로 보완 필요 | 독립 |
| 근거 검증 화면 | 원문·주장 나란히 보기 가능 | 대화 중심 → HTML 보고서로 보완 | 독립 |
| 긴 문서 처리 | 분할·요약을 직접 통제 | 대화 용량·구독 사용량 한도 | 독립 |
| 망분리·오프라인 | 로컬 모델로 가능 | 인터넷 필요 | 해당 없음 (개인 노트북은 인터넷 가능) |
| 유지보수 | API·OS 변화에 직접 대응 | AI 앱의 발전을 그대로 활용 | MCP |

병원 망분리가 개인 노트북에 적용되지 않으므로 독립 프로그램의 가장 큰 고유 장점(오프라인 동작)이 이 사용 환경에서는 필요 없다. 남은 독립 프로그램의 장점(일관성, 검증 화면, 긴 문서 통제)은 아래 설계 원칙으로 대부분 보완할 수 있다.

**MCP 서버 설계 원칙**

1. **도구는 단계 단위로 크게 만든다.** `analyze_lineage(project)`, `supplement_methods(project)`처럼 한 단계를 엔진이 정해진 순서로 실행하고, LLM에게는 판단과 서술만 맡긴다. 잘게 쪼갠 도구만 주면 실행마다 단계가 빠지거나 순서가 바뀐다.
2. **상태는 프로젝트 폴더에 둔다.** `project.json`에 단계별 완료 여부, 근거 목록, 확인 수준을 기록하고, 앞 단계가 끝나지 않으면 다음 단계 도구가 실행을 거부한다. 대화가 끊겨도 이어서 할 수 있다.
3. **결과는 파일로 쓰고 대화에는 요약만 돌려준다.** 논문 본문과 참고문헌 전문을 대화에 그대로 넣지 않는다. 대화 용량과 구독 사용량을 아낀다.
4. **인용은 도구만 만든다.** 서지 정보는 PubMed·Crossref 조회 결과로만 채우고, LLM이 쓴 인용은 ID 대조를 통과해야 산출물에 들어간다.
5. **검증은 HTML 보고서로 한다.** 주장-근거 대조표(원문 위치, 확인 수준, 의심 항목)를 브라우저로 열어 확인하게 한다. 지원하는 앱에서는 MCP 화면 확장을 선택적으로 쓴다.
6. **안내 프롬프트를 함께 제공한다.** MCP의 프롬프트 기능으로 "저널클럽 준비 시작" 같은 정해진 시작점을 두어, 레지던트마다 다른 방식으로 시작하지 않게 한다.
7. **마지막에 품질 점검 도구를 둔다.** `check_project`가 빠진 단계, "확인 못 함" 주장 수, 라이선스 불명 그림을 보고하고, 통과해야 공유용 산출물을 만든다.

**레지던트 직접 준비 방식에서 생기는 문제와 대응**

| 문제 | 대응 |
|---|---|
| **레지던트마다 구독이 필요** (계정 공유는 약관 위반) | 기본 지원 앱 하나를 정하고 필요한 요금제를 안내한다. 구독이 없는 사람을 위한 API 키 CLI 경로를 남겨 둔다 |
| **구독 사용량 한도** | 논문 1편 처리에 드는 사용량을 파일럿에서 측정한다. 원칙 3으로 사용량을 줄이고, 단계마다 나눠 실행할 수 있게 한다 |
| **설치 부담** (Python, OCR 도구, Docling 모델 수백 MB) | Claude Desktop 확장 패키지(.mcpb)처럼 실행 환경을 묶은 설치본을 만든다. Windows에서 Tesseract·Ghostscript 설치가 걸림돌이면 스캔본 OCR은 첫 사용 때 받는 선택 구성요소로 둔다 |
| **레지던트 간 품질 차이** | 원칙 1, 6, 7로 흐름을 고정하고, 지도교수 검토를 공유 전 단계로 둔다 |
| **AI 앱마다 동작 차이** | 기본 지원 앱 하나에서 평가 세트로 검증하고, 다른 앱은 "동작 가능, 미검증"으로 안내한다 |

**공용 클라우드 폴더 공유**

- 프로그램은 클라우드 서비스에 직접 올리지 않고, 사용자가 지정한 **동기화 폴더**(Google Drive, OneDrive, Dropbox 등의 PC 폴더)에 공유용 묶음을 내보낸다. 서비스별 연동과 로그인 처리를 만들 필요가 없다.
- 공유용 묶음: 학습 PDF, 슬라이드, 근거 대조 보고서, 서지 목록(DOI 링크 포함).
- **원문 PDF와 참고문헌 원문은 공유 묶음에 넣지 않는다**(1.4절 5항). 다른 레지던트는 서지 목록의 DOI 링크로 병원 와이파이에서 직접 연다.
- 슬라이드의 논문 그림은 2절 6항의 라이선스 기준을 따른다.

**공용 서버 PC 검토 결과 (결정: 만들지 않음)**

| 방안 | 판단 |
|---|---|
| A. 공용 자료 저장소 | 공용 클라우드 폴더로 같은 효과 (1.7절) |
| B. 처리 서버 (OCR, 문서 생성) | 설치 실패가 잦을 때만 도입. 병원 와이파이의 기기 간 통신 차단(AP 격리), IT 승인, 운영 부담 때문 |
| C. 처리 + AI 서버 (기관 API 키) | 레지던트 구독 비용이 부담될 때 Phase 6과 함께 검토 |

**독립 데스크톱 앱을 다시 검토할 조건** (파일럿 후 판단)

- 구독 비용이 레지던트에게 부담이 되어, 기관 API 키로 일괄 지원하는 편이 낫다고 판단될 때
- HTML 보고서만으로는 근거 검증이 불편하다는 피드백이 많을 때
- 기본 지원 앱의 정책이나 MCP 지원이 크게 바뀔 때

### 1.7 공용 코퍼스와 중복 방지 (결정: 노트북 MCP + 클라우드 폴더)

**구조**: MCP 서버는 각 레지던트 노트북에서 실행하고, 코퍼스는 공용 클라우드 폴더(PC 동기화 폴더)에 둔다. 한 사람이 받거나 OCR한 문헌은 다른 사람이 다시 받거나 처리하지 않는다.

**폴더 구조**

```
JournalClub/                       공용 클라우드 폴더
├── corpus/
│   ├── fulltext/
│   │   ├── oa/                    오픈 액세스 원문 (공유 가능)
│   │   ├── licensed/              구독 원문 (공유 범위는 도서관 확인에 따름)
│   │   └── scan/                  도서관 스캔본 원본
│   ├── abstracts/                 PubMed 초록 (PMID별 파일)
│   ├── supplements/               보충자료
│   ├── derived/                   OCR 결과, Docling 구조 추출, 본문 텍스트
│   └── records/                   문헌당 기록 파일 1개
└── seminars/
    └── 2026-11-05_jpis-56-189/    발표별 공유 묶음 (학습 PDF, 슬라이드, 근거 보고서, 서지 목록)
```

작업 중인 프로젝트 폴더(중간 결과, `project.json`)는 각자 노트북에 두고, 완성된 공유 묶음만 `seminars/`로 내보낸다.

**중복 판정**

1. DOI(소문자 정규화) → 2. PMID → 3. 제1저자·연도·제목 앞부분 순으로 같은 문헌인지 판정한다.
2. 파일 해시값(SHA-256)으로 이름만 다른 같은 파일을 걸러낸다.
3. 조회·다운로드 전에 `records/`를 먼저 확인하고, 있으면 건너뛰고 "보유 중"으로 표시한다.
4. 초록만 있던 문헌의 원문이 들어오면 추가하고 확인 수준을 "초록 확인 → 전문 확인"으로 올린다.

**중복 OCR 방지**

- OCR·Docling 결과는 `derived/`에 **원본 파일 해시값 + 처리 도구 버전**을 이름으로 저장한다. 같은 원본·같은 버전이면 다시 처리하지 않는다 (Löe 1965 기준 11쪽 약 54초 절약).
- 처리 도구 버전이 올라가도 기존 결과는 지우지 않고, 필요할 때만 새 버전으로 다시 처리한다.

**클라우드 동기화 폴더에서 생기는 문제와 대응**

| 문제 | 대응 |
|---|---|
| 목록 파일 하나를 여러 사람이 동시에 고치면 동기화 충돌 | 데이터베이스 파일 대신 **문헌당 기록 파일 1개**. 쓰기는 임시 파일에 쓴 뒤 이름 바꾸기로 한 번에 |
| 동기화가 늦어 두 사람이 같은 문헌을 동시에 처리 | 처리 시작 시 작업 표시 파일(`.lock`: 사용자, 시작 시각)을 두고, 오래된 표시는 무시. 그래도 겹치면 결과 파일 이름이 해시값 기반이라 같은 결과가 되어 해가 없다 |
| 충돌 사본 생성 ("파일 (1).json" 등) | 엔진이 충돌 사본을 찾아 병합하거나 보고 |
| 필요할 때만 받는 동기화 방식(파일 스트리밍, 주문형 파일) | 처음 열 때 느릴 수 있다. `records/`, `abstracts/`, `derived/`는 "오프라인 사용 가능"으로 설정하도록 안내 |
| 사람마다 폴더 경로가 다름 | 설정에 코퍼스 위치만 저장하고, 기록 파일 안의 경로는 모두 상대 경로 |
| **레지던트가 수련을 마치고 계정이 정리되면 그 사람이 올린 파일이 사라짐** | 교수 계정 소유 폴더 또는 기관 공유 드라이브(Google 공유 드라이브, SharePoint 등)를 쓴다. 개인 드라이브의 공유 폴더는 파일 소유권이 올린 사람에게 남는다 |
| 저장 용량 | 원문 1편 2-5MB 기준 1,000편에 약 5GB. 600dpi 스캔본은 더 크므로 스캔본 크기를 측정해 계획 |

**다시 받지 않아도 다시 확인할 것**: 철회(retraction)·정정(erratum) 여부는 서지 정보로 주기적으로 확인한다. 철회된 논문은 기록에 표시하고, 이를 근거로 쓴 세미나 자료가 있으면 알린다.

## 2. 새로 추가할 사항

1. **근거 추적 (가장 중요)**
   모든 문장 단위 주장에 [출처 문헌 ID, 원문 위치(쪽·문단), 확인 수준]을 저장한다. 산출물에서 확인 수준을 표시하고, 원문을 확인하지 못한 주장은 눈에 띄게 구분한다.

2. **사람 검토 단계**
   ①②③ 각 단계 결과를 편집 가능한 문서(마크다운)로 먼저 보여 주고, 지도교수나 발표자가 고친 뒤에 PDF와 슬라이드를 만든다. 자동 생성 결과를 그대로 발표하지 않게 한다.

3. **평가용 논문 세트와 품질 기준**
   유형별 3-5편(총 15-20편)을 골라 기대 산출물의 기준을 정한다. 예: "생략된 방법 항목을 몇 개 찾았나", "인용 오류를 찾았나", "만들어 낸 인용이 0건인가". 프롬프트나 모델을 바꿀 때마다 이 세트로 다시 점검한다. 첫 사례(jpis-56-189)가 첫 기준 자료다.

4. **기관 양식 지원**
   병원·학교의 PowerPoint 템플릿(.potx)과 PDF 양식을 불러와 쓸 수 있게 한다.

5. **언어 선택**
   한국어 / 영어 / 혼용(의학 용어는 영어 병기). 세미나 관례에 맞게 선택한다.

6. **저작권 기준**
   논문 그림을 슬라이드에 넣을 때 라이선스(CC BY, CC BY-NC 등)를 확인해 표시하고, 출처를 자동으로 단다. 라이선스가 불명확한 그림은 넣지 않고 "원 논문 Figure N 참조"로 대체하는 옵션을 둔다.

7. **세미나 이력과 지식 누적**
   발표한 논문, 정리한 연구 흐름, 확인한 문헌을 쌓아서 다음 논문 정리에 다시 쓴다. 같은 연구팀의 후속 논문이나 같은 주제가 나오면 이전 기록을 연결한다.

## 4. 단계별 로드맵

기간은 1인 개발 기준의 대략적인 추정이다.

### Phase 0. 기반 정리 (1-2주)

- [ ] 요구사항과 이 로드맵 확정 (8절의 결정 사항)
- [ ] 평가용 논문 세트 선정: 유형별 3-5편
- [ ] 첫 사례(jpis-56-189)를 기준 자료로 정리
- [ ] 기술 결정 기록(ADR) 작성: 언어, MCP 우선 구조(1.6절), 기본 지원 AI 앱
- [ ] 저장소 기본 설정: 폴더 구조, 테스트, 코드 스타일, 라이선스

**완료 기준**: 평가 세트와 품질 기준표가 있고, 기술 결정이 문서로 남아 있다.

### Phase 1. 처리 엔진 핵심 (4-6주)

- [ ] PDF 해석: 본문 섹션, 그림·표 위치, 참고문헌 목록 추출 (PyMuPDF, 선택적으로 GROBID)
- [ ] 스캔본 처리: 텍스트 층 확인 → OCRmyPDF → Docling 구조 정리, 숫자·표 이중 판독(OCR + 이미지 LLM 또는 RapidOCR), 표 내부 일관성 검사 (1.5절)
- [ ] 참고문헌 → DOI/PMID 매칭 (Crossref, PubMed)
- [ ] 문헌 조회 모듈: PubMed, Europe PMC, Crossref, OpenAlex, Unpaywall
- [ ] 프로젝트 폴더 구조와 `project.json` (단계 상태, 근거 목록, 확인 수준)
- [ ] 코퍼스 저장 계층 (1.7절): 폴더 분리, 문헌당 기록 파일, DOI/PMID/해시 중복 판정, OCR 결과 재사용. 처음부터 코퍼스 위치를 설정으로 받아 로컬 폴더와 클라우드 폴더에서 똑같이 동작
- [ ] 근거 추적 데이터 구조와 확인 수준 표시
- [ ] 논문 유형 판별 (출판 유형 정보 + LLM + 사용자 확인)
- [ ] CLI: 엔진 시험과 평가 세트 실행용 (`jca analyze paper.pdf`)

**완료 기준**: 엔진 도구들이 평가 세트의 Original article에서 첫 사례와 같은 근거 자료(전작 방법, 인용 대조)를 찾아 프로젝트 폴더에 기록한다.

### Phase 2. MCP 서버 (3-4주)

- [ ] 단계 단위 도구: 프로젝트 시작, 유형 확인, ① 맥락, ② 보강·검증, ③ 결과 해석, 산출물 생성, 품질 점검 (1.6절 원칙 1-7)
- [ ] 안내 프롬프트: "저널클럽 준비 시작"
- [ ] 근거 대조 HTML 보고서
- [ ] 공유용 묶음을 동기화 폴더로 내보내기
- [ ] 설치 패키지(.mcpb 등): Windows, macOS 개인 노트북. 스캔본 OCR은 선택 구성요소
- [ ] 레지던트용 설치·사용 안내 (1쪽)
- [ ] 논문 1편당 구독 사용량 측정

**완료 기준**: 레지던트 1명이 안내서만 보고 자기 노트북에 설치해 Original article 1편을 처리하고, 만들어 낸 인용이 0건이다.

### Phase 3. 유형별 처리와 산출물 (4-6주)

- [ ] Original article 하위 유형별 점검표 (RCT, 관찰, 동물, 진단)
- [ ] SR/MA 처리: PRISMA/AMSTAR 2 점검, 보충자료 입력, 포함 연구 표, GRADE 정리
- [ ] Narrative review 처리: 주장-근거 대응표, SANRA 점검
- [ ] 산출물 생성: 학습용 PDF, PowerPoint 슬라이드(발표자 노트 포함), 기관 템플릿 적용
- [ ] 그림 추출과 라이선스·출처 표시

**완료 기준**: 세 유형 평가 세트 전체에 대해 PDF와 슬라이드가 생성되고, 지도교수 검토 점수가 기준을 넘는다.

### Phase 4. 원문 접근과 코퍼스 (3-4주)

- [ ] 기관 프록시 링크 설정 (병원 밖 사용 시, 기관별로 한 번)
- [ ] "필요한 원문" 목록 (HTML): DOI / 프록시 / PubMed 링크, "병원 와이파이에서 열기" 안내
- [ ] 다운로드 폴더 감시 → DOI로 짝짓기 → 코퍼스에 추가
- [ ] 오픈 액세스 원문 자동 수집 (Unpaywall, Europe PMC)
- [ ] 원문을 받은 뒤 확인 수준 자동 갱신 (초록 확인 → 전문 확인)
- [ ] 공용 클라우드 폴더 운영: 작업 표시 파일, 충돌 사본 처리, 철회·정정 주기 확인
- [ ] 코퍼스 검색 (공용 폴더 전체)

**완료 기준 추가**: 레지던트 두 명이 같은 참고문헌을 인용할 때 두 번째 사람은 다운로드와 OCR 없이 기존 결과를 쓴다.

**완료 기준**: 첫 사례 기준으로, 참고문헌 원문을 사용자가 클릭 몇 번으로 받아 코퍼스에 넣고 2단계를 다시 돌릴 수 있다.

### Phase 5. 파일럿 운영 (한 학기, Phase 2 완료 후 시작 가능)

- [ ] 실제 저널클럽에 적용 (레지던트가 직접 준비 → 공용 폴더 공유)
- [ ] 사용 기록과 피드백 수집: 시간 절약, 수정량, 발견한 오류, 구독 사용량, 설치 문제
- [ ] 평가 세트 확장, 프롬프트와 점검표 개선
- [ ] 독립 데스크톱 앱 필요 여부 판단 (1.6절 재검토 조건)
- [ ] 교육 효과 측정 (선택: 교육 연구로 발전 가능)

### Phase 6. 독립 데스크톱 앱 (조건부, 5-8주)

파일럿에서 1.6절의 재검토 조건이 충족될 때만 진행한다. 엔진은 그대로 재사용한다.

- [ ] Tauri 셸 + Python 엔진 묶음
- [ ] 화면: 근거 검증·편집 중심 (원문 위치와 주장 나란히 보기)
- [ ] LLM 연결: API 키(OS 보안 저장소) + 로컬 모델, 비용 미리 보기
- [ ] 설치 파일, 코드 서명과 공증, 자동 업데이트

**완료 기준**: 구독 없이 기관 API 키만으로 MCP 경로와 같은 품질의 결과를 낸다.

## 7. 첫 사례에서 얻은 교훈 (설계에 반영)

1. **인용을 실제로 열어 봐야 가치가 생긴다.** ref 29와 ref 30의 문제는 원문 대조로만 찾을 수 있었다. → 근거 추적과 원문 대조가 핵심 기능이다.
2. **전작(같은 연구팀의 이전 논문)이 가장 중요한 보강 자료다.** → 저자·연구팀 기준 문헌 탐색을 기본 기능으로 넣는다.
3. **방법 보강에는 계산과 환산이 자주 필요하다.** (용량 계산, 마취제 mg/kg 환산) → 가정을 명시한 계산 결과를 별도로 표시한다.
4. **PDF는 한국어 글꼴, 슬라이드는 사용자 PC 글꼴 문제가 있다.** → 글꼴 내장(PDF)과 기본 글꼴 선택(PowerPoint)을 설정으로 둔다.
5. **결과물 검토에 시간이 든다.** → 미리보기 화면과 단계별 편집이 필요하다.
